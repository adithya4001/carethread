GlucoAhead

A little foresight. Better care.

A focused Type 2 diabetes digital twin proof-of-concept for the Happiest Health Digital Twin Challenge 2026. Static patient history and dynamic synthetic CGM/wearable signals enter the same working forecasting model. A doctor-facing dashboard shows the next 60 minutes, and a replay compares a frozen prediction with subsequent readings.

Research demonstration. All supplied patients and sensor records are synthetic. This project has no demonstrated clinical validity and must not guide diagnosis or treatment.

Try the project

Open dist/GlucoAhead.html in a browser for the standalone app. No installation is required. Keep the dist folder together so document and CSV links resolve.

A Site was registered, but publication was blocked by the runtime approval policy. No live deployment is verified. The hackathon requires a public GitHub repository; a private Sites source repository would not satisfy that requirement.

Local requirements: Node.js 18 or later. No npm installation or API key required.

npm start

Open http://localhost:4174. Alternatively serve the dist directory with any static HTTP server. Opening index.html directly via file:// will not load JSON assets correctly.

What works

Three unseen synthetic demo patients: rising glucose, steady glucose, and a falling trend.

EHR and CGM/wearable context fused at every inference step.

Twelve forecast values at five-minute intervals, covering the next 60 minutes.

Play, pause, step forward, reset, stream speed, three/six-hour chart history.

Empirical residual band and a note when the central forecast crosses a demo reference.

Editable EHR inputs update the actual model output.

Prediction replay freezes a forecast before revealing future readings and errors.

Sensor CSV import with input validation and in-browser inference.

JSON snapshot download with EHR inputs, current reading and forecast values.

Evidence page with measured results, baseline, EHR ablation and failure counts.

There is no hospital integration, authentication system, real sensor connection or treatment recommendation. Data replays from local JSON. Edits and CSV imports are in memory and reset on reload. The interface labels this clearly as a synthetic demonstration.

Healthcare use case

A reviewer examines one simulated patient with Type 2 diabetes. The virtual patient updates as CGM readings arrive. The model estimates the next hour and highlights a central prediction above 180 mg/dL, or below 70 mg/dL. These values serve as demo references. Actual targets can differ for an individual.

The early-warning benchmark measures a predicted reading above 180 mg/dL in the next hour, excluding windows where the patient is already above that value. It does not treat a current elevated reading as an early warning.

Reference for CGM ranges: https://www.niddk.nih.gov/health-information/professionals/diabetes-discoveries-practice/clinical-targets-for-continuous-glucose-monitoring-data

Technical stack and model

UI: buildless HTML, CSS and JavaScript ES modules. Responsive SVG charts.

Training: Python and NumPy. Multi-output ridge regression, penalty 30.

Inference: dist/core.js applies the learned dist/model.json weights in the browser.

Model: standardized features predict glucose change from the current reading at each horizon, then add that change to the current glucose.

Inputs: glucose lags at 0/5/10/15/30/45/60 minutes; recent trends; rolling mean and population standard deviation; heart rate; steps over 30 minutes; sleep summary; age; BMI; HbA1c; diabetes duration; cyclic time-of-day; an HbA1c/trend interaction.

Future meal times, future glucose, and future activity never enter inference.

Bounds: output clipped to 40-400 mg/dL as an engineering guardrail. This is not a safety guarantee.

Dataset and reproducibility

No patient data or third-party clinical dataset is included. The original synthetic generator is in model/train.py, under this repository's MIT license.

Seed: 20261018. Each simulated patient has three days of five-minute glucose, heart-rate and step observations. The generator creates meal-response curves, circadian variation, activity effects, correlated noise and sensor noise. It is not a validated physiology simulator or an implementation of Synthea.

Split by patient: 80 training patients, 20 validation patients, 30 test patients. Training, validation and test windows never share a patient. Within a partition, windows overlap and are not statistically independent. Standardization uses training data only. Validation residuals set pointwise 10th/90th-percentile bands; test data is used only for evaluation and the explicitly disclosed demonstration examples.

The shipped app works without Python. Retraining regenerates the model, patients, metrics and sample CSV in the model directory. The committed test fixtures check Python/JavaScript inference parity for the shipped model; a changed model requires regenerating those fixtures.

The model misses most new spike windows, particularly when a future meal has not started. Its upper-threshold alerts therefore have limited sensitivity. EHR improvements partly reflect relationships built into this generator. High measured performance on a simulator would not establish generalization to real patients. No confidence probability, clinical sensitivity guarantee, or treatment effect is claimed.

CSV schema

Four columns, in any order: minute,glucose,heart_rate,steps. Each minute value must be a nonnegative integer, ascending at exactly five-minute intervals. At least 13 and at most 5,000 rows. Maximum file size 1 MB.

Input limits: glucose 40-400 mg/dL, heart rate 30-220 beats/min, steps 0-2,000 per five-minute interval. Missing values, infinities and irregular intervals are rejected. Sleep and EHR values come from the selected patient's editable context. Import copies that context to an in-memory imported patient. A sample file is provided at model/sample-patient.csv.

Replay needs at least 25 rows, comprising 13 history samples and 12 subsequent readings. A forecast can still run at the final reading because it does not depend on the future outcome.
